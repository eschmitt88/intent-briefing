# Writing effective tools for agents — with agents

## TL;DR

Anthropic's guide to designing MCP tools for agents. It recommends an
eval-driven loop: prototype the tools, generate realistic multi-step eval
tasks, then let Claude Code read the eval transcripts and refactor the tools.
The only measured result is two bar charts. On held-out test sets,
"Claude-optimized" MCP servers beat "human-written" ones: Slack 67.4% → 80.1%,
Asana 79.6% → 85.7% test-set accuracy. The optimized version changes tool
implementations and descriptions together, so the gain can't be credited to
descriptions alone. No n, no variance, and the task sets are not released.

## Claims

Measured (internal; no n, CIs or task set released):
- Held-out test-set accuracy, human-written vs Claude-optimized MCP server.
  These values exist only in the chart images, which the fetcher transcribed
  into the raw file:
  - Slack tools: 67.4% → 80.1% (+12.7 pts).
  - Asana tools: 79.6% → 85.7% (+6.1 pts).
  The text says the held-out sets showed gains "even beyond what we achieved
  with 'expert' tool implementations—whether those tools were manually
  written by our researchers or generated by Claude itself."
- A concise `response_format` uses "~⅓ of the tokens" of the detailed one in
  the Slack example (72 vs 206 tokens). This is one illustrative response,
  not an eval.
- Resolving UUIDs to semantic names (or 0-indexed IDs) "significantly
  improves Claude's precision in retrieval tasks by reducing
  hallucinations". No numbers.
- Prefix vs suffix namespacing has "non-trivial effects" on tool-use evals
  and varies by LLM. No numbers.
- Claude Sonnet 3.5 reached SOTA on SWE-bench Verified "after we made precise
  refinements to tool descriptions". This post gives no number and no
  ablation.

Asserted (design guidance, no numbers):
- Write tool descriptions as for "a new hire on your team". Make implicit
  context explicit (query formats, niche terminology, resource
  relationships), and enforce inputs/outputs "with strict data models"
  (`user_id`, not `user`).
- Build fewer, consolidated, workflow-shaped tools (`schedule_event`,
  `search_logs`, `get_customer_context`) rather than API wrappers. "More
  tools don't always lead to better outcomes."
- Error and truncation messages are steering text: give actionable fixes
  rather than tracebacks. Claude Code caps tool responses at 25,000 tokens by
  default.
- Eval tasks should be realistic and multi-call. Don't overfit expected-tool
  lists, "because there might be multiple valid paths". Verifiers should not
  be overly strict.
- Anecdote: Claude appended "2025" to web-search queries until the tool
  description was fixed.
- "Most of the advice in this post came from repeatedly optimizing our
  internal tool implementations with Claude Code."

## Methods / basis

- Practitioner account. The evals were built on Anthropic's internal
  workspace ("real projects, documents, and messages"), with held-out test
  sets to check for overfitting. The loop: concatenate eval-agent
  transcripts, paste them into Claude Code, let it refactor tools and
  descriptions.
- Metrics they say they collect: top-level accuracy, runtime, number of tool
  calls, tokens, tool errors. Only accuracy is reported.
- The method (not the data) is released as a tool-evaluation cookbook.

## Results

- Two point estimates (above). Gains are larger where the human baseline is
  weaker (Slack). No sample size, no task count, no seeds, no model named for
  the eval agent.

## Critique / open questions

- **Evaluation quality.** These are task outcomes with verifiable responses,
  which is the right kind of metric, and the held-out split is a real
  safeguard. But the reader can't size the effect: no n, no variance, no
  task description, and a single vendor lineage (Claude optimizing tools for
  Claude). The verifier "can be as simple as exact string comparison...or as
  advanced as enlisting Claude to judge", and the post doesn't say which was
  used.
- **Bundled intervention.** "Claude-optimized" covers implementation
  changes (consolidation, response formats, pagination) and description
  rewrites together. **The candidate summary's framing, "measured eval gains
  from agent-refined tool descriptions", overstates this.** The measured
  gain is for agent-refined *tool servers*. Description-only effects are
  asserted, not isolated.
- **On the 2x2.** A tool description is reference context, not a procedure.
  The advice is verbose on context (what a new hire would need), terse on
  procedure, with a warning against overspecifying expected strategies in
  evals. Hard input contracts go into schemas (code), not prose.
- **Q5 (author bias).** This is a counterpoint to "LLM-written context
  hurts". LLM-authored tool text improved outcomes, but only inside a
  measure-and-iterate loop against held-out tasks, with transcripts as
  evidence. That loop is the difference from unguided generation.
- **Q3.** "Clearly describing (and enforcing with strict data models)
  expected inputs" puts the invariant in the schema.

## Trust signals

- **Credibility:** 3. First-party measured numbers on held-out sets from the
  model vendor, a named author, and a released eval cookbook. Held back from
  higher because there is no n or variance, the tasks are internal, the
  intervention is bundled, and the post is not peer reviewed.

## Follow-up

- **Relevance:** 4. One of the few measured results on LLM-authored
  instruction text (tool descriptions/specs) beating human-written text on
  held-out task outcomes. It bears on P6 and Q5. Tools are adjacent to
  briefs, not the same thing.
- **Guide:** P6 refines. LLM-refined tool servers beat human-written ones
  (+12.7 and +6.1 pts held-out), so the suspicion should be aimed at
  *unvalidated* LLM-written context, not LLM authorship as such.
- **Guide:** P2 supports. "Describe your tool to a new hire" and make the
  implicit context explicit; the "2025" query bug was a missing requirement.
- **Guide:** P3 supports. Input contracts go into strict schemas, not prose.
- Candidate follow-up: the tool-evaluation cookbook as a repo/doc snapshot,
  if it states task counts.
